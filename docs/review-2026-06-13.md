### 1 — GraphRAG graph-mode traversal does not owner-filter intermediate path nodes
**Severity:** Low · **Area:** multi-tenant isolation (R1) · **File:** `src/AgentMemory.Neo4j/Retrieval/Internal/GraphRetriever.cs:105,125`

**What's wrong.** `BuildTraversalCypher` scopes the `seed` and the final `related` endpoint to
`(owner OR shared)`, but the variable-length pattern `MATCH path = (seed)-[:RELATED_TO*1..N]-(related)`
places **no predicate on the intermediate nodes** of the path. A scoped graph-mode recall can therefore
*route through* another owner's private node to reach an owned/shared endpoint.

**Why it matters (and why only Low).** Intermediate node **text is never emitted** — `RETURN`/`FormatGraphResult`
join only `seedText → relatedText`, so there is **no direct content leak**. The residual risk is an
**inference side-channel**: `hops = length(path)` *is* returned as metadata, so a scoped caller can observe
that a connecting path of length N exists, confirming a bridging node lives in another owner's subgraph
(without learning what it is). It also makes graph-mode the one R1 surface that doesn't scope consistently.
Reachable because cross-owner `RELATED_TO` edges can legitimately exist (`RelationshipQueries.Upsert` stamps
`r.owner_id` but never constrains the two endpoints to share an owner) and `GetContextAsync` passes
`request.UserId` as the owner.

**Best fix (lowest-risk).** When `scoped`, add one path-wide predicate after the variable-length MATCH:
`WHERE all(n IN nodes(path) WHERE n.owner_id = $owner_id OR n.owner_id IS NULL)`. Because `seed` and `related`
are members of `nodes(path)`, this one clause subsumes the endpoint filters uniformly. **Gate strictly behind
`scoped`** so the unscoped/admin query stays byte-for-byte identical, and apply to **both** the `γ≥1.0` and
`γ<1.0` branches. Add a unit test (scoped cypher contains the predicate; unscoped does not) and an integration
test (`A1-[:RELATED_TO]->X(owner B)-[:RELATED_TO]->A2`; a scoped recall for A returns no `A1→A2` bridge).

### 2 — Lifecycle-operation coverage is asymmetric across node types (undocumented)
**Severity:** Low · **Area:** API consistency · **File:** `src/AgentMemory.Abstractions/Services/ILongTermMemoryService.cs`

**What's wrong.** The three long-term node types get inconsistent lifecycle surfaces on the service:
`Invalidate*` exists for all three; `Supersede*` exists for Fact and Preference but **not Entity**; public
hard-`Delete` exists **only for Preference** (`DeletePreferenceAsync`) even though `IFactRepository.DeleteAsync`
and `IEntityRepository.DeleteAsync` exist on the repos. A consumer discovers by trial that they "can delete a
preference but must invalidate a fact/entity" and "can supersede a fact but not an entity."

**Why it matters.** Pure discoverability/coherence — no behavioral, correctness, or security impact.

**Best fix (lowest-risk).** This asymmetry is *partly intentional*: the codebase has an explicit
invalidate-not-delete philosophy (`docs/bitemporal-memory-assessment.md` — hard delete is a deliberate,
narrow GDPR/TTL escape hatch, not the default), and `:SUPERSEDED_BY` is documented as Fact→Fact / Preference→
Preference only. So **don't broaden the destructive surface** — instead add a type-level `<remarks>` block to
`ILongTermMemoryService` stating: (a) all three types are closed via `Invalidate*`; (b) supersession is
Fact/Preference only (mirrors `:SUPERSEDED_BY`); (c) hard delete is intentionally exposed only for preferences;
use `Invalidate*` for facts/entities, or the repository `DeleteAsync` for explicit policy deletes.

### 3 — `nextsteps.md` lists a no-op "Package Rename" as the #1 HIGH open task
**Severity:** Low · **Area:** docs/drift · **File:** `docs/nextsteps.md:7,32,141`

**What's wrong.** The Priority Matrix (line 32) and §4 Step 1 (line 141) present
"Package Rename (`AgentMemory.* → AgentMemory.*`)" as the highest-priority *open* task — a literal **no-op**
(source == target), clearly a botched find/replace of the original `Neo4j.` prefix. Meanwhile line 62 says
"Package rename is complete (merged 2026-04-30)" and the tracking table marks it done. The canonical
forward-looking doc thus lists a finished rename as both the top open priority *and* as done.

**Best fix (lowest-risk).** Treat the rename as historically complete: remove it from the Priority Matrix and
§4 Step sequence (renumber the rest so DELETE_SESSION_DATA / Aspire / Release shift up), and where the history
is recorded, correct the transformation to the real `Neo4j.AgentMemory.* → AgentMemory.*` so source ≠ target
reads sensibly. Update the §4 rationale that justified "#1 because NuGet IDs are permanent."
