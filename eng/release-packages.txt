# Canonical inventory of packages published to NuGet on release.
# Format: <PackageId>|<ProjectPath>
# Adding a project under src/ does NOT publish it — it must be listed here first.
#
# A project may instead be declared HELD:<PackageId> to say it exists under src/ and is deliberately
# NOT published on any line, or PREVIEW:<PackageId>|<ProjectPath> to put it on the 0.x preview line,
# released only by its own preview-v<0.x.y-prerelease> tags. The consistency check
# (eng/check-release-manifest.sh) accounts for every src/ project, so a new one can never be forgotten.
# eng/release-lines.sh is the one reader of this grammar.
#
# Why that is needed at all: the release packs every listed project with -p:Version=<tag>, which
# overrides the project's own <Version>. A package on a different version line cannot ride this
# release without being restamped to the core version, and restamping an experimental 0.x contract
# to 1.x would SemVer-lock it on the day it shipped — the exact thing its 0.x line exists to avoid.

# ── The 0.x preview line (40.27) ───────────────────────────────────────────────
# The extensibility SDK ships 0.x with [Experimental("AMEXT001")] while its contracts settle
# (spec decision 5: the attribute comes off when a second independent module passes conformance).
# Packing it at the core's version would freeze it at 1.x, and publishing an experimental SDK
# automatically with every core release is the wrong cadence besides. So it has its own tags,
# preview-v0.x.y-<prerelease>, which pack only these projects at the tag's version through
# -p:PreviewVersion (never -p:Version, which would restamp the core projects they depend on), after
# the core release they depend on is on NuGet. Validation packs (40.57, 40.26) ride the same line:
# the pack format is still settling, and module packs are the conformance kit.
